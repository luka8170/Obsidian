## 2. LLM-Wiki 패턴 (Karpathy)

> **"Obsidian = IDE, LLM = 프로그래머, Wiki = 코드베이스"**

### Raw / Wiki 분리 철학

| Raw              | Wiki                |
| ---------------- | ------------------- |
| 외부에서 들어오는 날것의 정보 | LLM이 Raw를 읽고 정제·보관  |
| 필터링 없이 저장 (불변)   | Claude가 소유, 사람은 읽기만 |
| Inbox            | Source of Truth     |

둘을 섞으면 안 된다 — Raw는 inbox, Wiki는 source of truth.

### 왜 Wiki가 강력해지는가

1. 시간이 쌓일수록 "내 기준을 통과한 것만" 모인다
2. 중복 없이 압축된 나만의 지식베이스 형성
3. LLM이 Wiki를 context로 쓸수록 나를 더 잘 이해한다
4. **1개월 → 3개월 → 6개월: 가치가 기하급수적으로 증가** (복리 자산)

### 운영 사이클

```
사람이 Raw에 정보를 던진다
       ↓
Claude가 읽고 Wiki 기준에 맞는지 판단
       ↓
통과 → Wiki의 올바른 위치에 분류·압축·저장
       ↓
비슷한 개념끼리 위키링크로 연결
```

### 슬래시 커맨드 체계

| 명령       | 역할                   |
| -------- | -------------------- |
| `ingest` | Raw 소화 → Wiki 정제 박제  |
| `query`  | Wiki 큐레이션 검색 (읽기 전용) |
| `lint`   | Wiki 구조 오류 진단        |

## 3. PARA Method — 티아고 포르테

> 디지털 지식을 **현재 실행 가능성** 기준으로 분류하는 4단계 시스템

| 카테고리         | 정의                 | Luka 예시           |
| ------------ | ------------------ | ----------------- |
| **P**roject  | 구체적 마감일이 있는 현재 목표  | 관세사 2026 1차 시험 합격 |
| **A**rea     | 지속적으로 유지해야 할 책임 영역 | 고객 관리, 건강, 가족     |
| **R**esource | 미래에 참고할 수 있는 정보    | 이 Wiki 전체         |
| **A**rchive  | 완료/비활성 항목          | 끝난 프로젝트, 구 자료     |

**핵심 인사이트**
- 출처/형식 기준이 아닌 "행동 가능성" 기준으로 분류
- "건강해지기"는 Area, "5월 30일까지 5kg 감량"은 Project
- **정보를 모으는 것이 아닌 필터링하는 시스템이 경쟁력**

### 3.1 PARA 실전 구분법 (2026-08 추가)
> 출처: 「PARA 체계적인 노트 정리법」(goldenrabbit.co.kr)

- **도서관식(주제별) 분류 vs 부엌식(목적별) 분류**: 노트가 늘수록 "이 노트가 어느 주제냐"를 고민하는 게 아니라 "지금 이게 왜 필요하냐"로 물어야 분류가 쉬워짐
- **Area vs Resource 구분 기준**: "1년 이상 안 봐도 삶에 지장 없나?" → 그렇다면 Resource(취미·참고자료), 아니라면 Area(건강·커리어·가족·투자처럼 방치하면 삶이 틀어지는 것)
- **직업 지식 자체는 Area가 아님**: "AI 활용법을 공부하고 정리하는 책임"은 Area이지만, 지식 그 자체(예: 배운 프롬프트 기법)는 Resource로 분류 — 안 그러면 세상 모든 지식이 다 내 책임(Area)이 되어버림
- **판단 순서**: 새 노트가 생기면 Project → Area → Resource → Archive 순으로 검토(중요도·긴급도 순). 새 노트 대부분은 Project일 확률이 높음
- **Inbox 활용**: 어디 넣을지 애매하면 일단 수집함에 넣고 나중에 결정 — 분류 고민으로 시스템 사용을 포기하는 것보다 낫다
- **노트 위치는 유동적**: 완료된 프로젝트는 Archive로, Archive의 노트도 필요해지면 언제든 부활 가능(쓰레기통이 아니라 잠재적 재활용함)

## 4. 효율 철학

### 초효율 — 타이탄철물점(오윤록)
> 열심히가 아니라 **효율적으로** 살아야 자본주의에서 이긴다

**핵심 원칙**
1. 효율 = 들인 노력 대비 얻은 결과. 주어진 24시간은 누구나 같다
2. 노동(시간 투입)으로는 절대 부를 만들 수 없다 → **시스템**이 필요하다
3. 부업 → 사업으로의 전환 경로:
   ```
   아르바이트(시간 판매) → 부업(기술/콘텐츠 판매) → 사업(시스템이 돈을 만듦)
   ```
4. **디지털 콘텐츠 상품**: 한 번 만들면 반복 수익 → 스마트스토어, 강의, PDF, 템플릿

**Luka 적용**
- 해운 25년 전문 지식을 디지털 상품화 가능한 주제 3개 선정
- Claude Code로 반복 업무 자동화 → 효율 극대화
- 성공한 사람(귀인) 가까이서 배울 기회 적극 찾기

### 업종 선택 시 피해야 할 특성
- 일회성 구매 (재구매 없음)
- 고객이 갑인 구조
- 경기 악화 시 마케팅비 급증
- 인구 감소 트렌드와 역행

## 5. 플랫폼 비즈니스 원리 — 강성호
> **"연결이 권력이고 돈이다"**

### 플랫폼 = 양면시장 연결자

```
소비자 ←→ [플랫폼] ←→ 판매자/광고주
```

**교차 네트워크 외부성**: 한쪽이 커지면 다른 쪽도 커진다 → 임계점을 넘으면 자동 성장

**교차 보조금 구조**
| 유형 | 구조 |
|------|------|
| 공짜 미끼 (넷플릭스 무료체험) | 미래의 나 → 현재의 나 보조 |
| 프리미엄 (유튜브) | 유료회원 → 무료회원 보조 |
| 광고 (카카오톡, 네이버) | 광고주 → 일반 사용자 보조 |

**핵심 전략**: 한쪽을 무료로 끌어모아 반대쪽에서 돈을 번다

**블록체인** = 신뢰 기계. 은행 없이도 신뢰 보장. 금융·물류·부동산 등 중개인이 필요한 분야 모두 변화 예상.

**Luka 적용**
- 해운 인사이트 무료 공유 → 팔로워 증가 → 유료 컨설팅 수요 (교차 보조금 구조)
- 해운 전문 지식을 플랫폼(클래스101, 탈잉)에 올려 수익화
- BV 영업에서 양면시장 구조 분석: 누가 돈을 내고 누가 혜택을 받는가?

## 6. K-AI 생태계 2026 — 젠슨황 만찬 분석

> "지금 이 자리에 있는 스타트업들에 당장 투자하세요!" — 젠슨황 (2026.06.08, 서울 신라호텔)

### 배경
- 2026년 6월 8일, 신라호텔 비공개 만찬 '코리아 AI 에코시스템'
- 스타트업 50곳+, 대기업·VC·정부·연구기관 총 200여명
- 핵심 질문: "GPU를 더 많이 사는 시장인가, GPU가 쓰일 다음 산업을 만드는 시장인가"

### 젠슨황이 주목한 K-AI 4개 영역

**🤖 피지컬AI (만찬의 주인공, 절반 차지)**
- 로봇 하드웨어: 위로보틱스, 홀리데이로보틱스
- 로봇 두뇌(파운데이션 모델): 리얼월드, 마키나락스, 마음AI
- 자율운항: 아비커스 (해운 관련!)
- "피지컬AI는 이제 시작이다" — 반복 강조

**⚙️ AI 인프라**
- GPU 간 통신: 포인투테크놀로지 / AI 경량화: 노타, 스퀴즈비츠
- LLM 개발: 업스테이지, 트릴리온랩스

**🏭 특화 AI**: 루닛(의료), 알세미(반도체 설계 자동화), SDT(양자컴퓨터)

**🎯 AI 활용**: 트웰브랩스(영상, 엔비디아 투자), 클레온(음성), 인핸스(AI 에이전트)

### 젠슨황이 한국을 주목하는 이유
1. "복잡하고 무거운 것들을 잘 만드는 나라" — 반도체·원전·조선 초정밀 제조 경쟁력
2. 올라운더 환경: 대기업 + 스타트업 + 플랫폼 기업 모두 존재
3. 빠른 실행력: 현장 적용·검증 속도 세계 최고 수준
4. 대기업·스타트업·VC·정부·연구기관이 연결된 생태계 구조

### K-AI 전략적 과제

**엔비디아 안에서 '내 것' 사수**
- 빌려 쓸 것(GPU, 클라우드) vs. 우리 것으로 남길 것(현장 데이터, 핵심 알고리즘, 고객 접점)
- 제조 데이터·현장 검증 경험·소프트웨어 레이어는 반드시 축적

**엔비디아와 호환되되 종속되지 않는 구조**
- 엔비디아 GPU 활용 + 독자 시뮬레이터·학습 방식·산업별 소프트웨어로 차별화

### Luka에게 주는 인사이트

**해운업 + AI 결합 포인트**
- 해운 현장 데이터(운임, 적하, 루트, 항만 운영) = 피지컬AI의 '라스트 마일' 소재
- K-AI 생태계 흐름: 범용 AI가 채울 수 없는 도메인 전문성 → Luka의 해운 25년 지식이 여기에 해당
- 자율운항(아비커스) 같은 분야: 해운 도메인 전문가의 현장 검증이 필수

## 9. git 히스토리 정리 — 대용량 파일 제거 (2026-10-22)
> 위 §8 하네스 개선 작업 직후 같은 세션에서 발생한 push 실패를 해결한 후속 기록. ingest 체계 자체의 배경은 [[second-brain-setup]] 참조

### 문제
- 커밋 `d6a3cf5`에 OneDrive 백업 폴더(1804개 파일, 4.4GB)와 개인 xmind/OneNote 파일(약 600MB)이 통째로 들어가 `git push`가 HTTP 500으로 계속 실패
- 근본 원인은 `.gitignore`에 해당 확장자(`.xmind`, `.one`)와 백업 폴더 경로가 애초에 빠져 있었던 것

### 한 일 / 해법
- 안전 백업 브랜치를 먼저 만든 뒤, 전체 `git clone --bare` + filter-repo 대신 **plumbing 명령(`read-tree`/`update-index --force-remove`/`write-tree`/`commit-tree`)으로 문제의 5개 커밋만 직접 재구성** — author/날짜/메시지 보존한 채 대용량 경로만 제거
- `update-ref`로 브랜치 포인터만 이동(`checkout`/`reset --hard` 미사용) + `update-index --force-remove`로 인덱스만 동기화 → working tree 파일은 전혀 건드리지 않음
- `.gitignore`에 백업 폴더 경로 + `*.xmind`/`*.one`/`*.onetoc2` 추가해 재발 방지
- 결과: push 용량 4.5GB → 602MB, 정상 push 성공

### 배운 것 / 인사이트
- **iCloud Drive 위의 `.git`은 대량 오브젝트 작업(clone/filter-repo)에 치명적으로 느릴 수 있다** — 파일 단위 I/O 지연 때문에 전체 재작성보다 "건드릴 커밋만 plumbing으로 재구성"이 훨씬 빠르고 안전
- **디스크 파일을 보존해야 할 때는 `checkout`/`reset --hard`를 쓰지 말 것** — `update-ref` + `update-index --force-remove` 조합이면 히스토리만 고치고 working tree는 무사함
- **대용량 파일 사고는 대개 `.gitignore` 확장자 누락에서 시작** — OneDrive/네이버 백업·OneNote·xmind처럼 비-텍스트 포맷이 섞이는 PARA 볼트 구조라면 사후 정리보다 확장자 기반 규칙을 사전에 넉넉히 깔아두는 게 낫다
