커밋 `d6a3cf5`("Vault cleanup")에 실수로 포함된 ~4.5GB짜리 대용량 파일 때문에 `git push`가 계속 HTTP 500으로 실패하는 문제를 해결했다.

## 문제
- 원인: OneDrive 백업 덤프 폴더(`3. Resource/Company one drive back up/`, 1804개 파일, 4.4GB)와 개인 xmind/OneNote 파일(한진해운 업무 기록.xmind 364MB, .one 파일 3개 합 230MB)이 한 커밋에 통째로 들어가 있었음.
- `.gitignore`에 `.xmind`/`.one` 같은 확장자나 해당 백업 폴더 경로가 빠져 있어서 애초에 걸러지지 않았음.

## 한 일
1. 안전 백업 브랜치(`backup-before-history-cleanup-2026-10-21`)를 먼저 만들어 원본 히스토리 보존.
2. `git clone --bare`로 전체를 복제해 filter-repo를 돌리려 했으나, `.git`이 iCloud 드라이브 안에 있어 오브젝트 하나하나 읽는 속도가 비정상적으로 느려(14시간 넘게 900MB도 못 끝냄) 포기.
3. 대신 **git plumbing 명령(`read-tree`/`update-index --force-remove`/`write-tree`/`commit-tree`)으로 문제의 5개 커밋을 직접 재구성** — 각 커밋의 트리에서 대용량 경로만 제거한 새 트리를 만들고, 원래 author/committer/날짜/메시지를 그대로 보존해 새 커밋을 체인으로 연결. 전체 복제 없이 로컬 오브젝트를 재사용해서 몇 초 만에 끝남.
4. `git update-ref`로 `main` 브랜치만 새 히스토리로 이동(→ `git checkout`/`reset --hard`를 쓰지 않아 작업 디렉토리는 전혀 건드리지 않음), `git update-index --force-remove`로 라이브 인덱스만 동기화(디스크 파일은 그대로 둔 채 git 추적에서만 제거).
5. `.gitignore`에 재발 방지 규칙 추가: 백업 폴더 경로 + `*.xmind`/`*.one`/`*.onetoc2`.
6. 최종 push 용량 4.5GB → 602MB로 줄어서 정상 push 성공 (`724fb6a..84076ab`).

## 배운 것 / 인사이트
- **iCloud Drive 위에 올려둔 `.git`은 대량 오브젝트 작업(clone/filter-repo)에 치명적으로 느릴 수 있다** — 로컬 디스크처럼 보여도 내부적으로 파일 단위 I/O가 느려서, 전체 복제 대신 "건드릴 커밋만 plumbing으로 재구성"하는 방식이 훨씬 안전하고 빠를 수 있다.
- **디스크 파일 보존이 목표라면 `checkout`/`reset --hard`를 쓰지 말 것** — `update-ref`(브랜치 포인터만 이동) + `update-index --force-remove`(인덱스만 수정) 조합이면 working tree를 전혀 건드리지 않고 히스토리에서만 파일을 제거할 수 있다.
- **대용량 파일 문제는 `.gitignore` 확장자 누락에서 시작되는 경우가 많다** — PARA 볼트처럼 OneDrive/네이버 백업, OneNote, xmind 같은 비-텍스트 포맷이 섞이는 구조라면 사후 정리보다 사전에 확장자 기반 규칙을 넉넉히 깔아두는 게 낫다.
